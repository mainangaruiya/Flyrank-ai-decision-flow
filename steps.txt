================================================================================
AI DECISION FLOW - MANUAL TEST STEPS
================================================================================
Everything below was run against this repo on 2026-08-19. Where a step is
already known to fail, it says so and explains why, so you can tell a new
regression apart from a known issue.

App under test:
  - UI          : http://localhost:3000  (single page, React Flow canvas)
  - Execute API : POST /api/workflow/execute
  - Inngest API : POST /api/inngest   (stub: logs the body, nothing else)
  - LLM call    : inngest/workflow.ts -> OpenAI chat.completions, gpt-4o-mini

0. READ THIS FIRST - BLOCKERS THAT WILL STOP YOU
--------------------------------------------------------------------------------
B1. The OpenAI key in .env is not billable. Every Run currently comes back:
        429 "Your account is not active, please check your billing details"
    Until this key is replaced with one on an account that has credit, NO
    end-to-end Run test can pass. Test sections 5 and 6 are blocked on this.
    Fix: put a working key in OPENAI_API_KEY and restart the dev server.

B2. You cannot connect two nodes by dragging in the UI.
    components/nodes/DecisionNode.tsx renders the text "YES ->" and "NO ->" but
    never renders React Flow <Handle> elements, so there are no connection
    points to drag from. To test any multi-node / branching flow you must build
    the graph as JSON and use the Import button (section 4) or hit the API
    directly with curl (section 6).

B3. `npm run build` fails. inngest/client.ts:3 passes `name:` to the Inngest
    constructor, which is not a valid ClientOptions property, so the type check
    at the end of the build errors out. `npm run dev` is unaffected - dev does
    not block on type errors. Do not treat a failing build as something you
    caused.

B4. Port 3000 may already be in use on this machine. Next will silently fall
    back to 3001 and print the real URL. ALWAYS read the port off the dev
    server output and use that everywhere below. If you curl 3000 while
    something else owns it you will get a confusing 404.

1. SETUP
--------------------------------------------------------------------------------
1.1  Node 18+ required. Verified working on v22.22.0.
       node -v

1.2  Install deps (only needed once, or after a git pull that touches
     package.json):
       npm install

1.3  Environment. This repo already has a .env with all four keys present:
       OPENAI_API_KEY, GROQ_API_KEY, INNGEST_SIGNING_KEY, INNGEST_EVENT_KEY
     Next loads .env automatically - you do NOT need to create .env.local even
     though the README tells you to. Confirm by watching the dev server banner,
     which prints:  "- Environments: .env"

     Only OPENAI_API_KEY actually affects the tests below. GROQ_API_KEY is
     unused by the code. The Inngest keys are unused too, because the Inngest
     integration is a stub.

1.4  Sanity check the OpenAI key BEFORE you start UI testing, so you know
     whether B1 still applies:
       curl -s https://api.openai.com/v1/models \
         -H "Authorization: Bearer $OPENAI_API_KEY" | head -5
     Expect a JSON list of models. If you see an error about billing or an
     inactive account, B1 is still in effect and sections 5-6 will fail.

     - If handles ever get added, the correct behaviour is: dragging creates an

4. TEST GRAPHS (paste these into Import)
--------------------------------------------------------------------------------
The runtime only needs id + data.prompt on nodes, and source/target/label on
edges. position and type are for the canvas. Labels must be uppercase YES/NO.

4.1  Two nodes, one YES branch:
{"nodes":[{"id":"n_1","type":"decision","position":{"x":50,"y":50},"data":{"prompt":"Is the value greater than 10?"}},{"id":"n_2","type":"decision","position":{"x":350,"y":50},"data":{"prompt":"Is the value greater than 100?"}}],"edges":[{"id":"e1","source":"n_1","target":"n_2","label":"YES"}]}

4.2  Full YES/NO branch off one root:
{"nodes":[{"id":"n_1","type":"decision","position":{"x":50,"y":150},"data":{"prompt":"Is the value greater than 10?"}},{"id":"n_2","type":"decision","position":{"x":350,"y":50},"data":{"prompt":"Is the value greater than 100?"}},{"id":"n_3","type":"decision","position":{"x":350,"y":250},"data":{"prompt":"Is the value negative?"}}],"edges":[{"id":"e1","source":"n_1","target":"n_2","label":"YES"},{"id":"e2","source":"n_1","target":"n_3","label":"NO"}]}

4.3  Single node, no edges (terminal case):
{"nodes":[{"id":"n_1","type":"decision","position":{"x":50,"y":50},"data":{"prompt":"Is the value greater than 10?"}}],"edges":[]}

4.4  Three-deep chain, tests that routing keeps walking:
{"nodes":[{"id":"n_1","type":"decision","position":{"x":50,"y":50},"data":{"prompt":"Is the value greater than 10?"}},{"id":"n_2","type":"decision","position":{"x":300,"y":50},"data":{"prompt":"Is the value greater than 20?"}},{"id":"n_3","type":"decision","position":{"x":550,"y":50},"data":{"prompt":"Is the value greater than 30?"}}],"edges":[{"id":"e1","source":"n_1","target":"n_2","label":"YES"},{"id":"e2","source":"n_2","target":"n_3","label":"YES"}]}

4.5  DO NOT RUN THIS ONE unless you are deliberately testing the cycle bug.
     evaluateNode recurses with no visited-set and no depth cap, so a loop
     spins forever, burning one OpenAI call per hop until the request dies.
{"nodes":[{"id":"n_1","type":"decision","position":{"x":50,"y":50},"data":{"prompt":"Always answer YES"}},{"id":"n_2","type":"decision","position":{"x":300,"y":50},"data":{"prompt":"Always answer YES"}}],"edges":[{"id":"e1","source":"n_1","target":"n_2","label":"YES"},{"id":"e2","source":"n_2","target":"n_1","label":"YES"}]}

6. API TESTS WITH CURL (fastest way to test routing logic)
--------------------------------------------------------------------------------
Set PORT first:
    PORT=3000     # or 3001 - whatever the dev server printed

6.1  Happy path, single node:
curl -s -X POST http://localhost:$PORT/api/workflow/execute \
  -H 'Content-Type: application/json' \
  -d '{"graph":{"nodes":[{"id":"n_1","data":{"prompt":"Is the value greater than 10?"}}],"edges":[]},"input":{"value":42}}'
     PASS: {"ok":true,"logs":[{"step":"node:n_1","result":"YES","raw":"YES"}]}

6.2  Same graph, input that should flip the answer:
     ...same as 6.1 but "input":{"value":2}
     PASS: result "NO". This is the single most useful check that the LLM call
     and the YES/NO parse are both actually working, rather than the code
     defaulting to NO on a malformed response - note that any reply not
     containing "YES" is silently treated as NO, so a broken call and a genuine
     NO look identical in the logs. Always test both directions.

6.3  Two-node chain (graph 4.1), input 42:
curl -s -X POST http://localhost:$PORT/api/workflow/execute \
  -H 'Content-Type: application/json' \
  -d '{"graph":{"nodes":[{"id":"n_1","data":{"prompt":"Is the value greater than 10?"}},{"id":"n_2","data":{"prompt":"Is the value greater than 100?"}}],"edges":[{"source":"n_1","target":"n_2","label":"YES"}]},"input":{"value":42}}'
     PASS: two log entries - node:n_1 YES then node:n_2 NO.
     CURRENT: {"ok":false,"error":"Error: 429 Your account is not active..."}
     (this is exactly the B1 failure, reproduced)

6.4  Edge-label casing. Repeat 6.3 with "label":"yes" (lowercase).
     PASS: the match is case-insensitive, so it should still route to n_2 and
     you should get two entries. If you only get one, label matching regressed.
     Now try "label":"Yes please" - EXPECTED: does not match, run stops after
     n_1 with a single entry. Matching is exact-after-uppercase, not substring.

6.5  Negative: empty graph
curl -s -X POST http://localhost:$PORT/api/workflow/execute \
  -H 'Content-Type: application/json' -d '{"graph":{"nodes":[],"edges":[]},"input":{}}'
     CURRENT: 500 {"ok":false,"error":"TypeError: Cannot read properties of
     undefined (reading 'id')"} - no nodes means no start node and the code
     dereferences undefined. It is caught and returned, so the server does not
     crash, but the message is not user-facing quality. Known issue.

6.6  Negative: no body
curl -s -X POST http://localhost:$PORT/api/workflow/execute \
  -H 'Content-Type: application/json' -d ''
     CURRENT: 500 {"ok":false,"error":"SyntaxError: Unexpected end of JSON
     input"}. Known issue - should be a 400.

6.7  Negative: missing graph key
curl -s -X POST http://localhost:$PORT/api/workflow/execute \
  -H 'Content-Type: application/json' -d '{"input":{"value":1}}'
     EXPECTED: a 500 with a TypeError. Same class of issue as 6.5.

6.8  Start-node selection. Give a graph where the first node in the array is
     NOT the root, e.g. list n_2 before n_1 with an edge n_1 -> n_2. The code
     picks the node with no incoming edges, so execution must still begin at
     n_1. PASS: first log entry is node:n_1, not node:n_2.

6.9  Inngest stub endpoint:
curl -s -X POST http://localhost:$PORT/api/inngest \
  -H 'Content-Type: application/json' -d '{"name":"test/event","data":{"a":1}}'
     PASS: {"ok":true}, and the dev server console prints
     "Inngest event received { name: 'test/event', data: { a: 1 } }".
     Verified working.
     Scope note: that is ALL this endpoint does. It does not register or run
     any Inngest function, and it does not verify the signing key - it will
     accept an unsigned request from anyone. Workflow execution runs inline in
     the Next request instead. So there is nothing to test in the Inngest
     dashboard, no step history, and no retries. Do not spend time looking for
     runs there.
     Also: POST only. A GET returns 405.
